# agent-data/v1 request samples

These samples show the requests entorhinal sends when moving one made-up agent
with one `opencode-session` reference. Each format is registered in a fresh
registry; the agent never has both references at once.

## Reference generation

The generator calls `cortexkit-role-llm-runner`, exactly pinned to `=0.7.19`
in `crates/entorhinal-module/Cargo.toml` under `[dev-dependencies]` only.
This crate is used to generate test samples, not by entorhinal in production.

| File | Generator | Exact inputs |
| --- | --- | --- |
| `old-format.json` | Deprecated `session_ref_v1(harness, project_root, session)` | `("opencode", "/workspace/agent-data-example", "session-example-001")` |
| `new-format.json` | `session_ref(&SessionIdentity { runner, harness, session })` | `runner: "thalamus-harness", harness: "opencode", session: "session-example-001"` |

Both references are generated by the published crate; neither is a manually
chosen opaque fallback. The new form in this release is **runner identity**, not
project identity: its inputs contain no project root or project ID. The old
per-folder helper is deprecated and remains available for stored legacy refs.

The generated old ref is `f0899fdab1ada701e021b02c77dc7be4`; the generated new ref
is `386b5b14bf78c68c559f922d7800b165`.

Entorhinal itself never computes session refs. It stores the ref core registers
and passes it unchanged to the participant. A participant must resolve the exact
`(ref_kind, ref)` through `agent.session_for_ref` and **echo refs byte for byte**;
it must not rehash, normalize, or replace an old ref with a new one. The binding's
`runner` is `thalamus-harness`, matching a hosted OpenCode session.

## Contents and capture boundary

Each JSON file is an array of sixteen records:

- Two registry records contain the full `request` (`method` and `params`), the
  core caller's principal (`reserved:prefrontal-core`), and the real handler's
  `reply`: `agent.register_session`, then `agent.session_for_ref`.
- Five `side: "source"` records capture `agent_data.describe`, `busy`, `prepare`,
  `export`, and `release` from a completed move.
- Four `side: "receiver"` records capture `agent_data.describe`, `diverged`,
  `import`, and `activate` from the same completed move.
- Five `side: "source-abort"` records capture `describe`, `busy`, `prepare`,
  `export`, and `abort` from an alternative run stopped after export. An aborted
  move cannot also release its source; these are separate fresh fixtures with
  the same single agent and reference.

Participant requests come from the real admission, `Source` and `Receiver` move
drivers through `ParticipantClient`, `SubcParticipantDiscovery`, and the real
subc consumer/service transport. A loopback fake daemon records each received
frame body **before parsing it**, then dispatches it to the stateful
`FakeParticipant`. The published `request` embeds those captured bytes, rather
than reconstructing requests from expected fields or re-encoding parsed JSON.
Participant replies are fixture responses, not published interoperability
samples.

The agent ID is `agent_0123456789abcdef`; source and receiver member IDs are
`01010101010101010101010101010101` and `02020202020202020202020202020202`.
Handlers use fixed incarnation `0123456789abcdef`; registration clock is `1000`.
The sample agent and session identifiers are made up; `opencode` and
`thalamus-harness` name the real harness and runner. The project root is the
platform-independent spelling `/workspace/agent-data-example`. The only
post-capture normalization is a literal
replacement of the random cut ID: `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa` for the
completed move and `bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb` for the alternative abort.
`describe` has empty params, and `busy` has refs but no cut ID; the cut-scoped
requests include the full `cutId` and refs, and `release` also includes `holder`.
The binding remains registered while the fixture marks its session process gone,
as required by move admission's idle check.

For example, the new-format source prepare request is:

```json
{"method":"agent_data.prepare","params":{"cutId":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","refs":[{"ref":"386b5b14bf78c68c559f922d7800b165","ref_kind":"opencode-session"}]}}
```

## Reproduce and verify

From the repository root:

```sh
ENTO_WRITE_SERVED_VECTORS=1 cargo test --workspace --all-targets --locked served_vectors_agent_data_requests_v1 -- --nocapture
cargo test --workspace --all-targets --locked served_vectors_agent_data_requests_v1
(cd test-vectors/agent-data-requests-v1 && shasum -a 256 -c SHA256SUMS)
```

The generator test is
`two_machine_acceptance::moves::agent_data_request_vectors::served_vectors_agent_data_requests_v1`.
It reuses the existing two-machine move harness, and runs an isolated child
process so the SDK's supervised launch identity cannot affect other tests.
Without the write flag it regenerates and byte-compares both files and their
`SHA256SUMS` on every CI run. It is also selected by the `served_vectors` test
filter. Existing sample sets and their checksums are not rewritten.
