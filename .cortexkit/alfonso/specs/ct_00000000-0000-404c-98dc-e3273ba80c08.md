## acceptance_sketch
Each test must fail when the behaviour it names breaks. Each slice reports one deliberate break per test and shows the failure.

1. **Confirmed Direct writes land.** After the cut, Direct `create`, `rename`, `dispose`, `update_tag` and `set_labels` each call the stub once and land once confirmed.

2. **Refused approvals write nothing.** `Declined`, `PresenceUnavailable` and `Unsupported` each refuse with their code and leave the journal, the generation and the agent tables unchanged. Sending the same request key again prompts again.
3. **No prompt for a doomed write.** Each of these refuses with its own code and none calls the stub:

   With the log disabled and with it enabled, a key already landed under the same op returns its cached reply without calling the stub, even with a changed body. The same key under another op refuses `request_key_reused_across_ops`. The pre-check completes while another task holds the writer lock, and leaves rows, claims, journal and pending writes unchanged.
4. **Core unchanged.** The same writes from `Reserved("prefrontal-core")` never call the stub. Their journal rows and reply bytes are byte-identical to today, with no `operator_confirmed` key.

6. **No lock across the prompt.** While a Direct create waits in a stub that holds the prompt open, a project write and a core agent write both complete. With the identity log enabled, a core agent write through the shared path completes too. Assert the order, not the time.
7. **One prompt at a time.** While one prompt is open, a second Direct confirmable write refuses `operator_confirmation_busy` without calling the stub. It refuses the same way after the first is approved while its write is still running.

In (c) the stub is never called. In (a) and (b) a stub that answers at once in the same poll as the closure still loses to the closure.

## constraints
### Which writes, from whom
- Operator-confirmable methods: `agent.create`, `agent.rename`, `agent.dispose`, `agent.update_tag`, `agent.set_labels`.
- Admission order for those methods, all before any prompt:
  1. A flow-scoped route refuses `flow_scope_not_admitted`, as today.
  2. `Reserved("prefrontal-core")` is admitted with no prompt, as today.
  3. `Direct` is admitted only through the confirmation flow below.
  4. Every other principal refuses `write_not_permitted`, as today.
- `agent.set_avatar`, `agent.set_github_identity`, `agent.merge` and `agent.import` from `Direct` keep refusing `direct_identity_write_not_admitted`.
- **Where the condition lives.** `authorize_write` and `admit` (`crates/entorhinal-module/src/main.rs:311-333`, `:448`) keep refusing Direct on all agent writes, on every entry. The confirmation flow lives only in the async `write_wait` (`crates/entorhinal-module/src/shared_write.rs:1256-1262`). It recognises Direct on a confirmable method before `admit` would refuse it, runs the pre-checks and the prompt, and after approval runs the mutation through a separate entry that takes the approval as an argument (for example `execute_confirmed(request, key, approval)`), never through `admit`. The synchronous `execute` and `handle_request` (`main.rs:649-671`) therefore stay unconfirmed and keep refusing Direct.

### Before the prompt
A prompt is shown only for a write that would land if approved now. These checks run in this order against committed local state, and none of them prompts:
1. **Log fence.** While the identity log is enabling or joining, `bootstrap_fence` refuses as today, before the replay lookup (`shared_write.rs:1275`). This applies to new and cached Direct requests alike.
2. **Decode and request key.** Malformed params refuse `invalid_request`, and a missing key refuses `request_key_required`, in today's order.
3. **Replay.** The Direct pre-check calls `RegistryStore::shared_request_cache(op, key)` in every log state, not only when enabled. It reads `registry_journal` on the read connection, returns a same-op hit whatever the body, and refuses a key bound to another op with `request_key_reused_across_ops` (`crates/entorhinal-core/src/pending.rs:34-61`). No body comparison is added.
4. **Before the cut.** With no `agent.cutover` marker, the write refuses `authority_not_cut_over`.
5. **Validation.** Every domain check the write performs (names, role shape, project alias resolution and workspace placement, `uq_live_head`, name claims, supervisor rules, unknown agent) runs on the read connection. That connection is read-only with `query_only=ON` (`crates/entorhinal-core/src/read_connection.rs:20-27`), so a rolled-back dry run can't run there. Instead, core splits `create` and the non-create arm of `agent_mutation_with_id` into two phases. A validate phase over `&Connection` returns the prepared row, claims and resolved values, and checks the live-head rule by query rather than by a failed INSERT. An apply phase writes them. The pre-check runs validate alone, and the write runs both. Validate draws no agent id, so sequential-id tests are unaffected.
6. **Summary too long.** The summary over the cap refuses `operator_summary_too_long`. It is never truncated.
7. **Busy.** At most one operator confirmation is outstanding in the process. The slot is an RAII guard taken here and held until the request ends: through the prompt and, after approval, until the confirmed write returns. It records the request's `RouteKey` and a latched cancellation signal (see "Caller route closed"). It is released when it drops, whether the request ends normally, hits a deadline, errors, or is cancelled because the request future was dropped. A second confirmable Direct write while the guard is held refuses `operator_confirmation_busy` at once.

The pre-check promises only these checks. After approval, any refusal the unchanged write path raises still applies, `identity_log_enabling` included: writer-lock contention, the fence re-read after the lock (`shared_write.rs:1293-1295`, so a log that began enabling or joining during the prompt refuses), catch-up and log settlement.

### The summary
- One function in `entorhinal-core`, used by the module's pre-check and by core's stale check after approval. It builds one line from the validate phase's output, which includes the target row for an existing agent. Every interpolated string is written with Rust `{:?}` formatting, whether it came from the request or the store. That covers names, tags, labels, agent ids, project ids and workspace ids, and escapes quote, backslash, control and non-printing characters. Ids are always written in full.
- One form per write:
  - `create <role> agent "<name>"<placement>[ supervised by "<name>" ("<agent_id>")] with tag "<tag>"`. Role words are `assistant`, `workspace head`, `head` and `hiree`. `<placement>` is ` for project "<canonical project id>"` plus ` in workspace "<workspace id>"` when the project is placed, or ` for workspace "<id>"` when the request names only a workspace, or nothing.
  - `rename agent "<name>" ("<agent_id>") to "<new name>"`
  - `retire agent "<name>" ("<agent_id>")`
  - `set tag of agent "<name>" ("<agent_id>") to "<tag>"`
  - `set labels of agent "<name>" ("<agent_id>") to "<l1>", "<l2>"`, or `… to none` for an empty set.
- The cap is 200 Unicode scalar values of the final escaped string. It is one constant beside the builder in `entorhinal-core`, and it's firm because the macOS prompt clips longer text. The refusal says to shorten the tag, the name or the label set. It never advises splitting, because `agent.set_labels` replaces the whole set.
- **Known limitation.** A tag (valid up to 256 bytes) or a label set whose summary exceeds the cap can be written only through core's relay, not by Direct.

### The prompt
- Entorhinal calls the daemon through its own async, object-safe trait: `#[async_trait] trait OperatorConfirmer: Send + Sync { async fn confirm_operator(&self, summary: &str, route: RouteKey) -> Result<(), OperatorConfirmError>; }`.
  - It is injected on `ProjectsHandler` the way the log connector is (`with_log_connector`). The `Unsupported` implementation is the default in `with_runtime`. Tests use a stub.
  - `route` is the `(channel, epoch)` key from `on_bind`. S3 maps it to whatever `operator.confirm { route }` expects.
- The errors are `Declined`, `PresenceUnavailable` and `Unsupported`.
- No store lock or writer lock is held while the prompt is up. Other reads and writes proceed normally, including core agent writes through the shared path.
- Results map to refusals:
  - `Declined` → `operator_declined`, "the operator declined this write at the prompt".
  - `PresenceUnavailable` → `operator_presence_unavailable`, "operator confirmation is unavailable on this machine".
  - `Unsupported` → `operator_presence_unavailable`, "this daemon does not support operator confirmation". It is never treated as allowed.
- Dropping the trait future cancels the confirmation. An approval binds only the request whose future received it, so a late answer to an abandoned prompt authorizes nothing.
- **Caller route closed.** A closed caller route counts as declined.
  - `on_route_gone` (`crates/entorhinal-module/src/main.rs:508-510`) removes the admission, as today, and then fires the busy slot's signal when the slot's `RouteKey` matches. The signal is latched: once fired it stays set.
  - The request captures its admission (`shared_write.rs:1262`, `main.rs:448-449`) before the slot exists, so a closure in between must not be lost. After installing the slot in pre-check 7, the request checks that its `RouteKey` is still in the route admissions; if it is not, the request ends `operator_declined` without calling the confirmer. Because `on_route_gone` removes before it signals, every closure is seen either by that recheck or by the signal.
  - `write_wait` races the signal against the prompt and, after approval, against acquiring the writer lock, polling the signal first, so a closure already recorded wins over a confirmation or lock that is ready at once. If the signal wins, the trait future is dropped, the request ends `operator_declined` with nobody to observe it, the slot is released, a later answer from the confirmer is ignored, and no mutation or append starts.
  - Once the writer lock is held the write runs to its end whether or not the route is still open. Cancellation cannot undo an append already sent: an append whose outcome is unknown may still land later as described under "Known limitation: recovered appends".
- **Budgets.** Entorhinal answers every confirmable Direct write within 270 s of receipt, in every case: confirmed and applied, declined, unavailable, or a refusal from the write itself.
  - The prompt may run until `received + 270 s`. A `confirm_operator` call still pending then counts as `operator_declined`. SUBC withdraws its prompt after 120 s and bounds its confirmation queue plus prompt to 240 s.
  - After approval, the write path takes its deadline as `min(approval + DEADLINE, received + 270 s)` and its settlement as `min(approval + SETTLEMENT, received + 270 s)`, in place of `received + DEADLINE` and `received + SETTLEMENT` (`shared_write.rs:17-18`, `:1287`, `:1314`). The clamped deadline bounds the writer-lock wait and catch-up; the clamped settlement bounds append settlement. A late approval therefore gets only the time left before `received + 270 s`.
  - Core and project writes keep receipt-relative budgets unchanged.
  - Nothing else cuts the request: the daemon puts no deadline on a pending request on a bound route (`subc-daemon/src/router.rs:1104-1168`, `forwarding.rs:3285-3352`; its only timer is the 12 s route.bind), and the SDK puts none on handler requests (`docs/designs/agent-identity-pinned-facts.md:82-91`). The CLI's 300 s call timeout is the outer bound.
- **Until S3.** Until subc-client-rs publishes the channel-0 helper, the production implementation returns `Unsupported`. On the served path (`write_wait`), Direct on the five methods then gets the first pre-check refusal that applies, or a cached reply, or `operator_presence_unavailable`, instead of today's `direct_identity_write_not_admitted`. Tests that call `authorize_write` directly (`writes_are_refused_unless_the_operator_or_the_executive_opened_the_route`) or go through the synchronous `handle_request` seam (the null-body admission cases) stay unchanged, because those seams keep refusing Direct. The new expectations go in tests that drive the served path.

### After approval
- The write takes the writer lock and runs exactly as for core, through validate and then apply, within the clamped budgets above. With the identity log enabled, it uses the shared write path, including its existing `head_moved` retries after catch-up and its resend of an uncertain append (`shared_write.rs:1315-1316`). The agent id for a create is drawn once before the loop (`shared_write.rs:1309-1313`), so a retry keeps it.
- **Stale check inside core.** The module cannot step in between validate and apply, because both run inside core's write transaction, on a worker thread under `shared_attempt` when the log is enabled. So core's mutation entry takes an optional approval (for example `agent_mutation_with_id(…, approval: Option<&OperatorApproval>)`, where the approval carries the approved summary). Inside the transaction, after validate and before apply, core rebuilds the summary and compares it byte for byte with the approved line. On a mismatch it refuses `operator_approval_stale` and writes nothing. This runs on every attempt, including each retry after catch-up. It covers a project moved to another workspace, an alias that now resolves differently, or the target renamed by core or by a remote entry. If validation itself now fails, that refusal is the answer. The write is never re-prompted, and a domain or stale refusal is final. Only the shared path's own retries and resends run within the approved request.
- **Journal row.** When an approval is present, `journal::record` writes the row with principal `direct` and `payload_json` `{"entry": …, "operator_confirmed": true}`, with the flag beside `entry`, not inside it. `AgentChangeEntry` denies unknown fields (`crates/entorhinal-core/src/agent/journal.rs:45-48`), so the flag must not go inside. Every reader takes only `payload["entry"]`:
  - the feed (`crates/entorhinal-core/src/agent/feed.rs:100-103`)
  - local replay (`crates/entorhinal-core/src/agent/journal.rs:116-121`)
  - the shared-log body (`crates/entorhinal-core/src/shared_entry.rs:216-218`)

  So `agent.changes` and `agent.snapshot` serve the same keys as for a core row, and the flag stays local and never enters the shared log. Core rows carry no `operator_confirmed` key and are byte-identical to today.
- **Known limitation: recovered appends.** The guarantee on principal and flag covers confirmed writes committed locally. If the append's outcome is unknown, the local transaction rolls back and leaves a pending row (`engram_outcome_unknown`). If the log did accept it, catch-up later applies it as the module's own entry through remote apply (`crates/entorhinal-module/src/catch_up.rs:288-296`). That journals it with actor `log`, principal `entorhinal` and payload `{entry, signer, key_id}`, with no `operator_confirmed` (`crates/entorhinal-core/src/remote_apply.rs:534-546`). Such a write lands without another prompt. Core's pending writes behave the same today. This design doesn't carry the flag through `pending_entry`.
- A confirmed `agent.create` from Direct sets no supervisor unless the request names one. Supervisor rules are unchanged.

## intent
The operator decided that agent identity must not depend on prefrontal-core: people may run a different orchestrator. Today every agent write in entorhinal is admitted only from `Reserved("prefrontal-core")`, and `Direct` callers are refused with `direct_identity_write_not_admitted` (`crates/entorhinal-module/src/main.rs`, `authorize_write`). So nobody can create, rename, retire or retag an agent without core.

Direct can't simply be admitted. The operator's terminal, the desktop app and every agent shell on the Mac all reach entorhinal as `Direct`, and the sandbox that would separate them is optional on self-hosted machines. Admitting bare Direct would let any agent mint agents.

The subc daemon is adding an operator-presence check: during a request, a module calls the daemon op `operator.confirm { summary, route }`. The daemon shows a Touch ID or password prompt with the module's identity and the summary text, and answers confirmed or refused. Nothing is minted or transferable. The approval is bound to the request because the module calls it inside that request, and the person approves that exact text.

End state:
- A Direct caller (the `ck agents` CLI, the desktop app, or anything else local) can create, rename, retire, retag and relabel agents. Each write lands only after the operator approves its exact description at the prompt.
- `ck agents` is a new operator CLI face for those writes and for reading agents.
- Core's relay (`Reserved("prefrontal-core")`) keeps working unchanged, with no prompt.
- Nothing about this works before the identity cut: before the `agent.cutover` marker, every agent write still refuses `authority_not_cut_over`, before any prompt.


## non_goals
- Avatar, GitHub identity and merge writes from Direct callers. They stay refused for Direct, as today.
- Agent-initiated writes (heads creating hires, consent cards through cingulate). That's the deferred phase 2.
- Residence: which session an agent lives in is core's, bound after core sees the agent through its replica.
- Writes before the identity cut, or any bridge into core's store.
- Confirming reads. Reads stay open to every principal, with no prompt.
- Admitting callers by callosum attribution. `CallOrigin` is attribution only, never authority.
