# Reviewed spec for campaign ct_00000000-0000-4069-98dd-fae062b83918

This is the reviewed spec this campaign's slice plan was cut from: the document folded from the spec review rounds. It supersedes the original draft `.cortexkit/alfonso/drafts/2026-10-12-head-workspace-from-project.md`, which predates review; do not work from the draft.

## acceptance_sketch
1. A new head and a new hiree store `workspace_id = NULL`, and their claims are keyed on their project's placement.
2. On a store holding imported heads with stale workspaces (some placed, some whose claim is keyed on their own project id), the preview lists exactly the agents that change, and the correction clears every stored workspace and moves exactly the stale claims. A second run journals nothing. Verify and rebuild are clean after it.
3. The correction refuses, writing nothing, when a live head's project is unplaced, and when two moved names collide in a workspace.
4. Moving a project with a live head and a live hiree to another workspace moves both claims, journals the project op then two `agent.set_namespace` entries, and passes verify and rebuild.
5. The same move into a workspace where the head's name is taken refuses with `name_conflict` naming both agents and the workspace, and journals nothing.
6. Placing a project with no live agents needs no prompt; the same placement with a live head from `Direct` prompts with the exact summary, and an approval that goes stale is refused.
7. Unplacing or removing a project with live agents, and removing a workspace that live agents are bound to, still refuse with `bound_by_live_agent`.
8. A retired head's claim never moves.
9. `agent.changes` from before a move carries the `agent.set_namespace` entries with the expected after-images, and the published vector matches the handler's bytes.
10. With sharing enabled on two nodes, a carried move and the correction converge on both, and a forged entry that moves another agent's claim is refused.


## constraints
### Create and reads
- `agent.create` for `head` and `hiree` stores `workspace_id = NULL`. The name claim is keyed on the project's placement, exactly as now (`validate_create`). Validation order and error codes are unchanged.
- Replies that echo the agent row (`agent.create`, `resolve`, `list`, digest) show `workspace_id: null` for heads and hirees. `agent.fleet_identity` already derives the workspace from placement and is unchanged.
- Every read that scopes agents by workspace takes a live head's or hiree's workspace from its active claim's `namespace_key` (`namespace_kind = 'workspace'`), not from the stored column. This covers `resolve_name`, which today matches by stored `workspace_id` and falls back to `global` (`crates/entorhinal-core/src/agent/reads.rs:260-333`): prefix scoping, hint preference and the `name_ambiguous` candidate strings (`<workspace>/<name>`) all use the claim's workspace. The slice lists every other read it changes (at least `list`'s workspace filter and `peer_roster`, if they read the column). Owner: s1.

### The new op: `agent.set_namespace`
- One journal op only: it joins `IDENTITY_CHANGE_OPS` (`crates/entorhinal-core/src/agent/journal.rs:19-29`), so `agent.changes`, rebuild and `enable_state::agent_history` handle it. It also joins remote apply's separate list `remote_apply::AGENT_OPS` (`crates/entorhinal-core/src/remote_apply.rs:20-29`), which is the only list `apply` accepts standalone agent entries from (`remote_apply.rs:438`). It is not in `MUTATING_METHODS`, `CONFIRMABLE_METHODS`, admission or the manifest. Owner: s1.
- Its entry is an `AgentChangeEntry` shaped like `agent.rename`'s: the full after-image row plus the claims it touched (the released claim, then the new active claim). A pure clear has an empty `claims`. Each one bumps `agent_generation` and `updated_at_ms`. Replay goes through `replay_agent_entry`. Released claims keep their history. The new claim is a normal `claims::claim` in the target namespace.
- Every carried or corrected head or hiree gets `workspace_id = NULL` in its after-image, so a carry on an imported row also clears it.
- s1 proves the entry with unit tests on hand-built entries (no carry or correction handler exists yet): replay, the `agent.changes` page, and remote apply accepting a received `agent.set_namespace` entry and refusing one carrying another agent's claim with "agent entry changes another agent's claim" (`remote_apply.rs:447-460`).

### Name checks (carry and correction)
- All checks run before any write. A moving name collides if another live claim holds it in the target namespace (`claims::check_name`), or if another agent in the same batch is moving the same normalized name into the same namespace. `check_name` alone misses the batch case, and `uq_active_claim` would then fail mid-write. Either collision refuses the whole operation with `name_conflict` and detail `{agent_id, holder_agent_id, workspace_id}` (the moving agent, the other agent, the target workspace). Nothing is journaled. The batch case has its own test fixture.

### Placement carries names
- Every operation that places a project or moves it to another workspace carries its live heads and hirees: `assign_workspace`, `register` with a workspace, `upgrade_implicit` with a workspace, `seed_import`, and every other call site of `ensure_project_attachment_allowed` or `ensure_project_unbound` that changes placement (not removal). The slice lists each call site it changes and why.
- On success, in one transaction: first the project op's journal row, which carries the `request_key` and is the `Action.seq` row as today (`crates/entorhinal-core/src/mutations.rs:678-711`), then one unkeyed `agent.set_namespace` row per carried agent, ordered by `agent_id`. Rebuild replays the same sequence, and the project op's replay does not refuse a placement change that has live agents bound.
- Unplacing or removing a project with live agents, and removing a workspace that live agents are bound to (`crates/entorhinal-core/src/agent/mod.rs:57-76`), stay refused with `bound_by_live_agent`.
- Operator approval applies only to `Direct`. Today `write_wait` prompts only when the principal is `Direct` and the method is in `CONFIRMABLE_METHODS`, and builds `OperatorApproval` from the precheck summary only on that path (`crates/entorhinal-module/src/shared_write.rs:2392-2448`). The placement writes take one confirmation argument with three values:
  - `NotRequired`: every non-Direct principal (the executive `reserved:prefrontal-core`, core) and every in-process store call (`RegistryStore::register`, `assign_workspace_at` in tests). These carry with no prompt and no approval.
  - `Approved(OperatorApproval)`: Direct after the prompt.
  - `NoPrompt`: Direct when the precheck found nothing to carry, and every Direct request on the synchronous `execute`/`handle_request` path, which never prompts (`shared_write.rs:2390-2391`). So a Direct placement that would carry is refused on that path with `operator_approval_stale`.
- Direct gate: `assign_workspace`, `register`, `upgrade_implicit` and `seed_import` join `CONFIRMABLE_METHODS`, and `precheck_agent_confirmation` gains these methods and a third outcome `AgentPrecheck::NoPrompt` (today it yields only `Cached` or `Ready`, `crates/entorhinal-core/src/agent/store.rs:508-511`). For these methods it, in order:
  1. returns `Cached(body)` when the request key is already committed under the method's op;
  2. runs the write's own refusals on the read connection (at least `not_found` and `name_conflict`, stored and batch) and returns that refusal, so a write that would fail never prompts;
  3. returns `NoPrompt` when no live head or hiree would be carried, keeping today's admission with no prompt;
  4. otherwise returns `Ready(summary)`.
- `write_wait` returns a `Cached` body for a non-`agent.` method unchanged and attaches `incarnation` only to `agent.` methods, as the probe arm already does (`shared_write.rs:2421`, `:2452-2456`).
- One function builds the summary for both the precheck and the in-transaction re-check: `move <project> to <workspace>: <names>`, names in `agent_id` order. For a `seed_import` that carries agents in several projects there is one such clause per project, in project-id order, joined by `; `. If the text would exceed `OPERATOR_SUMMARY_LIMIT` (200 scalars, `store.rs:496`), it lists as many names as fit, then `and N more`.
- Under the writer lock: with `Approved`, a recomputed summary that differs refuses with `operator_approval_stale`. With `NoPrompt`, finding agents to carry refuses with `operator_approval_stale`. Either refusal writes nothing.
- Before the switchover a carrying placement change refuses with `authority_not_cut_over`. On a flow-scoped route it refuses with `flow_scope_not_admitted`.
- The CLI verbs that send these placements (`ck workspaces assign`, `ck projects register`) wait as long as `ck agents` writes and print `AGENT_WRITE_NOTICE` (`crates/entorhinal-module/src/cli.rs:90`), so a prompt is not withdrawn by a client timeout.
- Carry tests cover: the Direct prompt; the executive route with no prompt; a direct store call; a Direct request into a taken name refused with `name_conflict`, confirmer never called, journal head unchanged; a Direct same-key retry of a committed carrying `assign_workspace` returning byte-identical bytes with zero confirmer calls and nothing appended; and a Direct sync `handle_request` that would carry refused with `operator_approval_stale` while the same request from the executive carries.

### The correction
- `agent.repair_workspaces({request_key})` is a write. It joins `MUTATING_METHODS`, `CONFIRMABLE_METHODS`, `agent_operation_description` and `shared_candidate`/`Write::decode`, so on an enabled log it takes the shared path. It is admitted only from `Direct`, with confirmation, and only after the switchover. Its precheck returns `Ready` with the counts summary, after the same cache lookup and refusal checks as above. The executive (`reserved:prefrontal-core`) is refused with the new code `direct_caller_required`, and `agent_principal_matrix_precedes_decode_keys_and_cached_replies_before_and_after_cutover` gains that exception.
- For each `head` or `hiree`: clear a non-NULL stored `workspace_id`. If the agent is live and its active claim is not keyed on its project's placement, move the claim there. Each changed agent gets one `agent.set_namespace` row, ordered by `agent_id`. A live head or hiree whose project is unplaced refuses the whole correction with `unresolved_workspace` and detail `{agent_id, project_id}`.
- Request key: the rows are journaled under op `agent.set_namespace`. The key goes on the last row, which is `Action.seq`, and the others are NULL. The cache is looked up under `agent.set_namespace`, because it is op-scoped (`crates/entorhinal-core/src/pending.rs:34-61`), and carries never key `agent.set_namespace` rows. A run with nothing to change journals and caches nothing, and a same-key retry is evaluated again. The literal `agent.repair_workspaces` never appears as a journal op.
- `every_agent_store_journal_op_is_an_identity_change_or_marker` scans every `"agent.…"` literal in the production halves of `store.rs` and `import.rs`, not journal ops (`crates/entorhinal-core/src/agent/journal.rs:137-151`). It is rewritten: it exempts the request-method literal `agent.repair_workspaces` by name, and its scanned sources gain every production file that journals `agent.set_namespace` (at least `mutations.rs`), so a stray `"agent.bogus"` literal there turns it red.
- Reply: `{"cleared": N, "moved": M, "seq": <last seq or null>, "generation": G}`, plus the `incarnation` the module adds to every agent write (`crates/entorhinal-module/src/agent_ops.rs:213-217`). The summary states both counts and fits the limit.
- Preview: a new read, `agent.preview_repair_workspaces({})`, named after `preview_attach_root` (`crates/entorhinal-core/src/root_keys.rs:269-274`). It is open to every caller that may call agent reads and has a line in `agent_operation_description`. It returns `{"changes": [{agent_id, name, role, project_id, clears_workspace, claim_from, claim_to}], "refusal": null | {code, message, detail}}`. `claim_from` and `claim_to` are `kind/key`, or null when the claim stays. The refusal is the one the write would raise, with the same detail. Before the switchover it is `authority_not_cut_over`.
- CLI: `ck agents repair-workspaces` prints the preview. If the preview carries a refusal, it exits `EXIT_REFUSED` (3, `crates/entorhinal-module/src/cli.rs:88`). `--yes` sends the write.
- Owner: core function and preview data in s2; admission, wire, CLI and descriptions in s3.

For a carry, `tables` holds the project delta. For a correction, `tables` is empty. `record_local_entry` builds it, after the closure's last append, when the transaction carries agents.

## intent
An agent belongs to a workspace in exactly one way. A workspace head stores its workspace and has no project. A head or hiree stores its project and no workspace: its workspace is always its project's current placement. An assistant has neither. This was prefrontal-core's original schema (its migration 076). It drifted when core's 2026-08-13 seed registered 29 heads' names under their own project id as a stand-in, and core's migration 082 then copied that stand-in into `agent.workspace_id`. Entorhinal ported core's post-082 shape, and the agent-identity switchover imports those rows unchanged, by operator ruling.

The design is agreed in `docs/designs/head-workspace-follows-placement.md`. This campaign implements it in entorhinal:

- Creating a head or hiree stores no workspace. Its name claim is still keyed on its project's placement (`namespace_kind = 'workspace'`, `namespace_key` = the placement), as today.
- Placing a project in a workspace, or moving it to another, carries the active name claims of its live heads and hirees into the target workspace, in the same transaction, after checking every name against the target. This replaces today's `bound_by_live_agent` refusal for placement changes.
- One operator write corrects the imported data after the switchover. It clears the stored workspace on every head and hiree, and moves every live head's or hiree's active claim that isn't keyed on its project's placement into that placement.
- Every agent change is journaled with an after-image, so verify, rebuild, `agent.changes` (prefrontal-core's replica feed) and the shared identity log carry it like any other agent write.

After release, the operator will run the correction, retire five unneeded heads with `ck agents retire`, and move three projects (`opencode`, `pi-mono`, `oh-my-pi`) out of `cortexkit` into a workspace each. Those are operator actions, not slices.


## non_goals
- Any change to the switchover import. `agent.import` stays verbatim: it writes whatever workspace and claims core holds.
- Workspace heads. They keep storing their own workspace, and removing their workspace stays refused while they're live.
- Allowing an agent-bearing project to have no workspace. Creating a head or hiree still needs a placed project (`unresolved_workspace`). Taking a project with live agents out of every workspace, or removing it, stays refused (`bound_by_live_agent`). Projects without live agents may stay unplaced, as today.
- Changing name-lookup semantics. `workspace:` prefixes, `workspace_id` hints and `name_ambiguous` with candidates behave as today. The only change is the workspace a head or hiree is matched under, which comes from its active claim (see constraints, Create and reads).
- Retired and merged agents. Their claims are never moved, so their names stay reserved where they were.
- Prefrontal-core's replica changes. Core accepts the new op and heads with no workspace on its side (external dependency).
- A schema CHECK forbidding a workspace on heads. Rebuild replays imported rows that carry one, so the invariant is enforced in code and reported by `verify`'s two agent mismatch kinds (constraints, Verify), not by the table.
