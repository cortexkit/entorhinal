## constraints
### The import-order guard
- The guard condition is: the store has zero agents and no `agent.cutover` marker. It applies to an empty registry too. An empty machine bootstrapping the log closes the import just as a populated one does, so the reviewed spec's acceptance 12 ("an empty machine with no agent.cutover marker enables successfully") is superseded: that machine now needs `--without-agents`.
- Where it runs. Only from state `disabled`, inside `enable_locked` after the head read (`crates/entorhinal-module/src/enable.rs:274-278`), so engram errors (unavailable, not a member, key unavailable) still come first. It runs before any write: a refusal leaves the journal, log state and fake log unchanged, and the state stays `disabled`. In order:
  1. `authority_not_cut_over` (agents without a marker), as today (`crates/entorhinal-core/src/enable_state.rs:125-137`).
  2. head = 0: the flag check, the guard, then today's bootstrap.
  3. head > 0 and an empty registry: today's join. Neither the guard nor the flag check is evaluated, because the marker comes from the bootstrap snapshot the joiner applies.
  4. head > 0 and a non-empty registry: read 1..head (see the writer section). If every entry is `signed_by_self`, run the flag check, the guard, then the supersede checks. Otherwise refuse `join_requires_empty_registry` with the counts, as today, and evaluate neither.
- A guard refusal is `agents_not_imported`. Its message says to run the agent import first, or to pass `--without-agents` when the fleet has no agents to import.
- `ck projects log enable --without-agents` sends `{"without_agents": true}`. Only then may a guarded branch write the zero-agent marker (`ensure_cutover`), exactly as today. The rules for the flag:
  - the flag check runs only where the guard runs (branches 2 and 4): there the flag is refused `invalid_request` when the store has agents or a marker, so it can never mask a real import;
  - on a join (branch 3) it is ignored, even when the store holds a marker from an earlier zero-agent import;
  - in `enabled` (idempotent Ok, as today), `enabling` (resume) and `joining` (catch-up) it is ignored, and so is its absence;
  - `enable_log` decodes params: an unknown key or a non-boolean `without_agents` is refused `invalid_request`;
  - the CLI accepts `--without-agents` only on `log enable`.
- Resume never re-checks the guard or requires the flag. That covers both `ck projects log enable` without the flag and the background worker calling `enable::resume` with no params. A `--without-agents` attempt interrupted after its first append completes, and writes the marker once in `finish_enable`.

### Authorship from engram
- `identity_log.read` marks each entry `signed_by_self: true|false`. Engram computes it from the roster pseudonym bound to the entry's signing key at the head it was signed under, so it survives key rotation. Entorhinal never learns, stores or shows a device id.
- Each read entry also carries `author`: the entry's own rotation-stable pseudonym (not the reader's), as exactly 32 lowercase hex characters. Entorhinal compares authors only for equality, holds them only in memory, and never stores, logs or shows them. Both fields are on engram master (commits d9ec33d and ee1d519); this checkout cannot confirm that, so the log-client slice starts by pinning them on engram's main. The client pin in `log_client.rs` moves from 9c567a5 to the engram build that serves them.
- `log_client::LogEntry` gains `signed_by_self: bool` and `author: String`. A reply that is missing either field, or whose `author` is not 32 lowercase hex characters, is a protocol error. Catch-up stalls on it exactly as it does on an undecodable entry today (health state 6). The in-tree fake log models both fields, with an explicit author per appending store.

### Agent histories a supersede may carry
A restored pre-enable copy shares the enabled store's claim-id sequence, so forked renames can reuse a `claim_id` for a different name. `write_claim` updates only `released_at_ms` on a `claim_id` conflict (`crates/entorhinal-core/src/agent/claims.rs:122-126`) and never removes claims. `uq_active_claim`/`uq_active_agent_claim` (`crates/entorhinal-core/src/agent/schema.rs:68-74`) and `uq_live_head`, one live head per project (`schema.rs:48-50`), are immediate. A superseding snapshot is therefore accepted only if it extends the agent history it replaces. Call the replaced history H: for the writer, the agent state built from entries 1..head; for a reader, its local agent tables. The snapshot extends H when all of these hold:
- every agent in H is present (otherwise `supersede_drops_agents`, naming the first missing id);
- no agent has a lower `agent_generation` or `name_version` than in H (otherwise `supersede_regresses_agents`);
- every agent with an equal `agent_generation` has a row identical to H's;
- every claim in H appears under the same `claim_id`, with the same `agent_id`, namespace, normalized and display name, normalization version and `claimed_at_ms`. Its `released_at_ms` is unchanged, or goes from null to a value;
- no new active claim takes a name that H holds active for a different agent;
- no live head in the snapshot takes a project whose live head in H is a different agent, unless that agent is terminal in the snapshot.

The last four violations are `supersede_forks_agents`, naming the agent. A name that H holds active never passes to a different agent across a supersede, even when its holder becomes terminal in the snapshot; a live head passes to another agent only when the old head is terminal in the snapshot. Every other such move is out of scope: the operator makes it after superseding (for a reused name, give the new agent another name on A2, supersede, then rename it), and the refusal message says so.

Write order. Today's snapshot install writes agents in the order the snapshot lists them, and each agent's claims in the order its entry lists them (`crates/entorhinal-core/src/remote_apply.rs:309-321`, `crates/entorhinal-core/src/agent/journal.rs:123-128`). That order is the sender's. The reader does not trust it for a superseding snapshot:
- it writes agents whose snapshot row is terminal first, then the rest, each group in `agent_id` order, so a retired head comes before its replacement;
- it sorts each agent's claims by `claim_id`, so releases come before the new active claim.

The reader appends the `agent.import` journal rows in that order, with the claims sorted. Replay runs in journal order, so it writes in the same order. Under these rules, `write_claim` produces exactly the snapshot's claim set.

### Superseding a machine's own snapshot (the writer)
- In branch 4, enable reads the whole log, 1..head, paged as today. A supersede proceeds only if all of the following hold. Each refusal happens before `begin_enable`, leaves the state `disabled` and appends nothing:
  - every entry 1..head is `signed_by_self` (otherwise `join_requires_empty_registry`);
  - the flag check and the import-order guard pass;
  - entries 1..head end on a complete snapshot boundary, with no snapshot missing parts at head. Otherwise refuse `identity_log_invariant`, naming the position. Readers could never reach a new snapshot that starts inside an incomplete one (`crates/entorhinal-module/src/catch_up.rs:198-206`). Recovering a log whose own bootstrap was abandoned partway is out of scope. This rule does not apply to resuming a saved plan (state `enabling`);
  - the new snapshot extends the history of 1..head (see above). Readers would have to refuse it otherwise, so the writer must not publish it.
- A supersede appends a fresh snapshot of the current local state, built by today's `prepare_enable`, with base head `base` = head.
  - Wire part p (1..=parts, numbered as `partition` numbers them: `crates/entorhinal-core/src/enable_state.rs:114-118`) is sent with `expected_head: base + p − 1` and must land at position `base + p`. For example, `base` = 1 with two parts sends expected heads [1, 2] and lands at positions [2, 3].
  - Every part's body carries `supersedes_through: base`.
  - `partition` sizes candidate parts with `body(id, usize::MAX, usize::MAX, …)` (`enable_state.rs:89-106`). That estimate must include `supersedes_through` at its maximum width, so every part stays at or under 200 KiB.
- The saved plan records `base`. A plan saved by an earlier build has no base field and reads as `base` = 0: it resumes as a bootstrap with its original ids, bytes and expected heads, and the guard is not applied retroactively. Resume reads from `base`, not from 0, and resends only the parts not yet confirmed, each with its original expected head.
- `head_moved` on part 1: re-read position `base + 1`.
  - If it holds this plan's part 1 entry id, stay `enabling` and continue, as today's bootstrap does (`crates/entorhinal-module/src/enable.rs:182-205`).
  - If it holds a different entry, abandon to `disabled` and return `identity_log_contended`. The operator re-runs, which re-reads and re-checks; enable never retries blindly.
  - `head_moved` on part p > 1 is `identity_log_invariant`, and the state stays `enabling`, as today (`enable.rs:207-211`).
  - No other member's entry can land between parts, because members refuse shared writes while catch-up holds an incomplete snapshot (`catch_up.rs:242-249`). Engram's compare-and-swap does not stop another append between the read and part 1; it makes part 1 fail if one lands.
- On finish, `last_applied_position` and `last_seen_head` are set to `base + parts`, so this machine never applies its own superseded entries or its own new snapshot. The `identity_log.enable` journal row records `supersedes_through`.

### Applying a superseding snapshot (every reader)
- `SnapshotPart` gains an optional `supersedes_through`. Either every part of one snapshot carries the same value or none does; anything else stalls.
- A snapshot with `supersedes_through: S` is valid only if all of these hold:
  - S equals the first part's position − 1;
  - every entry at 1..S has the same `author` as every part of the snapshot;
  - it extends the reader's local agent history (see above).
- How the reader checks authorship. Members and restarted joiners have not read 1..S in this run, because catch-up reads from `last_applied_position` (`catch_up.rs:145-148`). So when a superseding snapshot is complete, catch-up re-reads `after = 0` through S, paged, within the same deadline. It compares authors in memory and then discards them. A failure of that re-read (unavailable, `verify_failed`, protocol error, deadline) is handled exactly like the same failure in the main read, and nothing is applied. A joiner that has just read 1..S takes the same re-read, so there is one path.
- Every supersede invariant failure has the same effect:
  - catch-up stalls with health state 6 and error code `apply_failed`, message `supersede invariant: <reason> at position <N>`, and applies nothing;
  - shared writes then refuse `identity_log_stalled` on an `enabled` member (`catch_up.rs:137-144`). A joiner is still `joining`, so its writes keep refusing `identity_log_enabling`;
  - the gauge lives in memory, so after a restart catch-up reaches the same position and stalls again.

  Without the author check, any member could erase another member's entries with one snapshot. The writer's `signed_by_self` check alone protects only honest writers.
- A valid superseding snapshot replaces the reader's shared state wholesale, in one SQLite transaction:
  - Shared rows (projects, workspaces, `project_root_key` and every other shared table) absent from the snapshot are deleted. Project and workspace deletes cascade machine-local rows exactly as a received delete does today (`crates/entorhinal-core/src/shared_entry.rs:380-422`).
  - Rows present in the snapshot are upserted, and the applied position advances.
  - Replacing is correct only because the author check guarantees that every replaced row came from the snapshot's own author. The code must say so where the replace happens.
- Root-key mappings. At the end of `ProjectEntry::restore`, after the upserts (`shared_entry.rs:291-347`), any entry that deletes a `project_root_key` row clears `project_root.root_key`/`root_key_kind` on every root whose `(project_id, root_key_kind, root_key)` no longer has a `project_root_key` row. Because the check runs after the cascade's successor moves and the upserts, a key moved to a successor (delete `(M,k)`, upsert `(S,k)`) keeps its mapping. `restore` runs on both apply and replay (`mutations.rs:1232`), so the two agree. A cleared root stays a root of its project with no key, still resolvable by path. `attach_match` looks up the chosen key before it checks the existing root (`crates/entorhinal-core/src/root_keys.rs:204-251`), so attach behaviour is unchanged and the limitation is:
  - if the root's chosen key no longer exists for the project, re-attaching refuses `root_key_not_found`, before and after `remove_root`. The root stays unkeyed until that key exists for the project again;
  - if the root's chosen key exists (for example its remote now yields the snapshot's replacement key), re-attaching refuses `root_conflict`. Recovery is `remove_root` then `attach_root`, which loses the root's approval.
- Journaling. `install_snapshot` keeps refusing received parts that carry deletes (`crates/entorhinal-core/src/remote_apply.rs:132-136`). The reader computes the absent-row deletes inside the apply transaction and puts them in the `delete` lists of the merged `ProjectEntry` stored in the first part's journal `entry`, alongside the upserts. That is the existing `TableChanges` format (`shared_entry.rs:26-42`), so no new field is needed. The received part bytes stay in the payload for audit, as today (`remote_apply.rs:172-198`). Replay applies those deletes with the same cascade and mapping clearing, so `verify` and `rebuild` reproduce the replaced tables.
- Agents are never deleted: tombstones are permanent, because core keeps foreign keys to them.
  - An agent that the snapshot adds, or whose row or claims differ, gets one `agent.import` journal row with the snapshot's after-image, as today's snapshot install writes (`remote_apply.rs:309-326`), in the write order above. That row is delivered through `agent.changes`.
  - An agent identical in both gets no journal row.
- A joining machine takes the same path: it applies the first snapshot, then the superseding snapshot replaces it. There is no separate "start from the newest snapshot" rule.
- A snapshot without `supersedes_through` at a position > 1 behaves as today. No writer produces one; this keeps old entries readable.

### Deployment and unchanged behaviour
- Order: upgrade engram first, then every entorhinal member, then supersede.
  - A new entorhinal reading from an engram without the fields stalls as a protocol error.
  - An old entorhinal stalls with `apply_failed` at any part carrying `supersedes_through`, because `SnapshotPart` denies unknown fields (`remote_apply.rs:48-58`). Once upgraded, it resumes from its unchanged applied position.
- With the log disabled, every reply and journal row stays byte-identical to today, and the existing invariance test keeps passing unchanged.
- `agent.import` is still never a shared write, and still refuses after the marker. Enable stays Direct-only.

## intent
Two defects surfaced when the shared identity log was first enabled on the operator's Mac. They have one root cause: enable assumed it was always the first and only bootstrap.

1. **Enable closed the agent import.** On a machine with no agents and no `agent.cutover` marker, enable writes the marker as an import of zero agents (`enable_state.rs` `ensure_cutover`). After that, `agent.import` refuses `import_already_done` (`agent/import.rs`). The reviewed identity-log spec says the import must run before enabling, but nothing enforced that order. So one operator command, run in the wrong order, silently closed prefrontal-core's only path for moving its 35 agents into entorhinal.
2. **Enable can't be undone and redone.** Engram's log is append-only by design: a rewound head is exactly what members treat as tampering. After the undo, the operator's store was restored to its pre-enable state, but the log still holds that store's first snapshot at position 1. Enabling again today refuses `join_requires_empty_registry`, because head > 0 and the registry isn't empty. Nothing can recover from this short of building a new path.

The end state:
- enable refuses to close the agent import by accident;
- a machine can supersede its own earlier snapshot, and only its own;
- every reader, joining or already a member, ends with exactly the newest snapshot's state plus the entries after it;
- this cannot be used to erase another machine's entries.


## non_goals
- Resetting or rewinding engram's log. That doesn't exist, by design, and won't.
- Superseding entries written by other machines, under any flag.
- Compaction or snapshot-triggered pruning of old log entries.
- Recording entry ids as a cache of authorship. `signed_by_self` and `author` are the authority.


## open_questions
- None on the design. Deployment dependency: `signed_by_self` and `author` ship in engram's next build. Code and tests land against the in-tree fake log; the live re-enable waits until a placed engram serves both fields.
